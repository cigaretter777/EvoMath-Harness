**Scope:** the one-shot dual-loop deliverable of
[`campaign-2026-09-27/preregistration.md`](campaign-2026-09-27/preregistration.md):
inner loop = a TIR cold-start SFT then an R4 GRPO continuation, both trained

SFT 56.5 m, GRPO 4 h 08 m (two interruptions included; training itself

## 1. The three arms

`all-tools` routing, temperature 0, max_new_tokens 1024, 200 tasks per arm,
3 shards, arms serial inside each shard. Rate columns are defined off the
merged trajectories and held to each run's own `summary.json`
(`artifacts/results/dual-loop-20260930/tool-use.json`).

| arm | tool-call rate | calls/task | tool success rate | accuracy |
|---|---:|---:|---:|---:|
| `base` | 1.5% | 0.030 | 50.0% (n=6) | **6.5%** (13/200) |
| `sft` | 96.5% | 0.965 | 65.3% (n=193) | **16.0%** (32/200) |
| `grpo` | 97.5% | 0.975 | 65.6% (n=195) | **16.5%** (33/200) |

Reading: the cold start moves the policy from "almost never calls a tool"
(1.5%) to "calls a tool on nearly every task" (96.5%) and buys +9.5 points of
accuracy. The R4 continuation sharpens on top of it — slightly higher call
rate and success rate, fewer invalid actions per task (0.185 → 0.15), shorter
trajectories at equal stability (`final` termination 92.0% → 90.5%) — and adds
+0.5 pt accuracy over SFT. The magnitude is honest: with a 50-step budget the
R4 signal is a refinement, not a second leap. `base`'s 50.0% tool success is
6 calls / 3 successes and is not a rate worth quoting; the `n=` column carries
the sample sizes.

Supporting metrics (`four-metrics.json`): `steps_mean` 5.76 / 2.07 / 2.03,
`invalid_actions_per_task` 5.595 / 0.185 / 0.15, `verifier_addressable_rate`
0.11 / 0.905 / 0.90. `routing_distribution {direct 76, python 66, sympy 58}`
identical on all three arms (equal to the pre-registered CPU prediction).

`data/processed/sft_tir_v1` (split manifest sha `5d89ad0d…`, pinned in
`configs/mvp/sft_tir.yaml`). 3,542 steps, `train_loss` 0.3219, final logged
loss 0.1772, `train_runtime` 3,392.6 s. Adapter + merged model on disk
(`adapter/COMPLETE` marker honoured by every later stage).

**GRPO ("R4 continuation").** 50 steps total (`save_freq` 10), LoRA r=16 α=32
on the TIR merge, batch 8, `env.rollout.n` 4, `max_steps` 6. Training ran in
two segments because of the outage below; **steps 31–50 are the second
segment's products** (the first segment's steps 31–39 were discarded with
resume-from-30). The learning signal rose across the run —
`episode/valid_action_ratio` 0.34 (step 41) → 0.418 → 0.526 → **0.657**
(step 47) → 0.459 (step 50), vs 0.317 at step 20 — i.e. the policy trades
turns for tool calls as the R4 reward teaches it to. Exported adapter: 392
LoRA tensors, `r=16`, `α=32`, provenance → `checkpoints/global_step_50`.

## 4. Interruptions and repairs (full account)

Three interruptions, two of them requiring a code repair, one a launcher
repair; the run reached 50/50 steps and a complete, un-flagged evaluation.

1. **Sandbox outage window C (step 16–20 contaminated).** The tunnel died
   17:29:46Z, flapped once, and stayed down; the pre-agreed sustained-outage
   policy stopped GRPO at step 20 (18:03Z, SIGTERM; the rc=134 was Ray
   teardown noise). Steps ≈16–20 rolled out with the python channel returning
   `unavailable` — bounded and annotated, no systematic collapse in
   episode/success-rate, **not re-rolled** (re-rolling would re-bet the
   tunnel for no signal purity). Checkpoint `global_step_20` intact; GRPO was
   resumed from 20 after the tunnel returned (`pong+42` ×4 probes).
2. **Sequence-length crash at step 40.** The step-40 rollout raised
   `NotImplementedError: sequence_length=4175 > max_length=4096`: one
   trajectory's tool-augmented history exceeded `data.max_prompt_length`
   (4096) and the shipped default `truncation: error` refuses to silently cut
   it. Repair `1c4cf8c`: `data.truncation=middle` (keep question head + newest
   turns, cut the middle) with a dated CHANGELOG in the config header.
   Raising `max_prompt_length` was rejected — the padded prompt length sizes
   the sequences the stack already carries (25.8 GB allocated on a 24 GB
   card) and history keeps growing, so a bigger ceiling only defers the
   crash. Not result-dependent: **no step up to 39 ever exceeded 4096**, so
   every already-trained step is untouched and the cut can only fire on what
   used to crash. Locally verified (4175→4096, head/tail preserved) and
   present in the resumed run's resolved config. Training resumed from
   checkpoint 30 (steps 31–39 re-rolled).
3. **Export gate filename bug (no loss).** At 22:16Z the chain reported
   `grpo: exported adapter has no config.json`. The training *and export had
   actually completed* (50/50; 392 tensors written) — the launcher's gate
   checked for `config.json`, a filename the exporter never writes
   (`export_verl_lora.py` lands `adapter_config.json` + a `COMPLETE` marker).
   Repair `a4c79bb`: both gates now check `COMPLETE`, the same finished-signal
   the SFT stage uses. Audited: these were the only two occurrences of the
   wrong name; the evaluation path always used `adapter_config.json`.

Two monitoring-only events are recorded for completeness: the session
watchdog's stall check did not include the eval `shard*.log` files (healthy
eval read as a 45-min stall; watch list fixed), and its chain-gone exit at
00:50Z was the *successful* chain exit. Neither touched any measurement.
